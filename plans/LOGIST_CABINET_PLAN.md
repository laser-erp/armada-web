# План: кабинет логиста — «Настройки кабинета» блоками

**Статус:** этапы 1–4 и 6a (MVP) · **в коде** 01.09.2026  
**Связано:** [ADMIN_PLAN.md](ADMIN_PLAN.md), [plan-seti.html](../plan-seti.html) (этапы B–E), [EXCHANGE_PLAN.md](EXCHANGE_PLAN.md), [EPD_SIGN_ONBOARDING_PLAN.md](EPD_SIGN_ONBOARDING_PLAN.md)

## 1. Цель

Единый экран **«Настройки кабинета»** (вместо разрозненных «Справочники», «Профиль», «Ссылки») — всё, что логист настраивает **до работы с заказами**, собрано **блоками**:

| Блок | Содержимое |
|------|------------|
| **Сотрудники** | Администратор кабинета, логисты (офис), права |
| **Свой автопарк** | «Наша фирма», водители, ТС, тариф, реквизиты |
| **Партнёры** | Заказчики, перевозчики; ручной ввод + **из сети АРМАДА** с автоподтягиванием парка после договора |

Операционная работа (**Парк / ЕТО / Биржа / Документы**) остаётся в текущем меню — настройки не дублируют заказы.

## 2. Что уже есть (не переписывать)

| Функция | Где сейчас | Перенос |
|---------|------------|---------|
| Карточка «нашей фирмы» (ИНН, банк, НДС, диспетчер) | Справочники → Компании | Блок «Свой автопарк» → «Профиль компании» |
| Водители + документы + PIN | Справочники → Водители | Блок «Свой автопарк» |
| ТС + ТО + СТС | Справочники → Авто | Блок «Свой автопарк» |
| Тариф ₽/км, ₽/ч | Справочники → Тариф | Блок «Свой автопарк» |
| Контрагент-заказчик + портал /z | Компания, роль «Заказчик» | Блок «Партнёры → Заказчики» |
| Контрагент-перевозчик (ручной) | Компания, роль «Перевозчик» | Блок «Партнёры → Перевозчики» |
| Личный профиль логиста | Профиль логиста | Блок «Сотрудники → мой профиль» или верхняя карточка |
| Ссылки QR/SMS | Входы и ссылки | Внутри соответствующих блоков (водитель, заказчик) |
| Биржа между кабинетами | Парк → Биржа, claim | Использует партнёра-перевозчика из блока «Партнёры» |
| Рамочный договор заказчика | `frameworkContract` в компании | Расширить на связь кабинет↔кабинет |

**Принцип реализации:** новый экран — **оболочка и навигация**; формы и store-функции переиспользуются (`openEditor`, `openDriverCard`, `fleetVehiclesForCompany`, …).

## 4. Модель данных (новое)

### 4.1. Связь кабинетов — `partnerLinks[]`

```js
{
  id, spaceId,                    // наш кабинет
  partnerSpaceId,                 // кабинет партнёра в АРМАДА (null = только локальная карточка)
  partnerCompanyId,               // companyId у нас (роль customer | carrier)
  roles: ['customer'] | ['carrier'],
  status: 'draft' | 'requested' | 'active' | 'revoked',
  requestedAt, acceptedAt,
  requestedByAdminId,
  // что запросили у партнёра
  shareScope: {
    drivers: true,                // ФИО, телефон, документы (без PIN партнёра!)
    vehicles: true,               // госномер, тоннаж, СТС-метаданные
    contacts: true
  },
  contract: {                     // рамочный договор между кабинетами (см. §4.4)
    status: 'none' | 'draft' | 'pending_sign' | 'signed' | 'revoked',
    templateId: 'partner-framework-v1',
    documentId,                    // id сгенерированного PDF/HTML в хранилище
    signMethod: null | 'paper' | 'edo',
    // подпись нашей стороны
    ourSignedAt, ourSignedBy, ourSignMethod,
    ourScanId,                     // опционально: скан с печатью (paper)
    ourEdoMessageId,               // id исходящего в ЭДО (edo)
    // подпись партнёра
    partnerSignedAt, partnerSignedBy, partnerSignMethod,
    partnerScanId, partnerEdoMessageId,
    edoOperator: null | 'kontur' | 'sbis' | 'diadoc'
  },
  lastSyncAt,
  syncMode: 'on_demand' | 'auto'  // auto — только после signed + обе стороны OK
}
```

### 4.2. Зеркало парка партнёра — не копия «навсегда»

- Локально: `partnerFleetCache[]` или поля на `company`: `linkedDrivers[]`, `linkedVehicles[]` с `sourceSpaceId`, `sourceDriverId`, `syncedAt`.
- **PIN водителя партнёра не копируется** — при назначении на рейс партнёр подтверждает своего водителя в своём кабинете (как сейчас claim на бирже).
- Документы (паспорт, ВУ, СТС): только после `contract.status === 'signed'` и явного `shareScope`.

### 4.3. Сотрудники — `admins[]` (расширение)

```js
{
  role: 'owner' | 'logist',       // owner = администратор кабинета
  permissions: ['orders', 'catalogs', 'billing', 'invite']
}
```

Супер-админ по-прежнему создаёт space в «Активность»; **owner** может приглашать логистов в свой кабинет.

### 4.4. Рамочный договор партнёра — PDF, бумага, ЭДО ✅ решено

**Требование продукта:** договор всегда **PDF** (из шаблона на бланке фирмы). Подписание — **два канала**:

| Канал | Когда | Как в UI |
|-------|-------|----------|
| **Бумага** | Сразу (MVP) | «Сформировать PDF» → «Печать» → подпись с печатью вживую → «Мы подписали» / партнёр «Подписали» → опционально загрузить скан |
| **ЭДО** | Когда оператор подключён | «Отправить через ЭДО» → окно оператора (Контур / СБИС / Диадoc) → статус из webhook |

Оба канала ведут к одному `contract.status === 'signed'`. Sync парка партнёра разблокируется только когда **обе стороны** подписали (любым из каналов).

#### 4.4.1. Генерация PDF

- Шаблон в **Конструкторе документов** (`doc-templates.js`): тип `partner_framework` — стороны, ИНН, предмет (обмен заявками / доступ к парку), `shareScope`, срок, реквизиты.
- Подстановка реквизитов из **наших** и **партнёрских** own-компаний (`space.ownCompanyId`).
- Кнопки: **«Открыть PDF»**, **«Печать»** — через `openPrintHtml` / `print-window.js` (как договор-заявка на рейс).
- Сохранение снимка HTML/PDF: `contract.documentId`, версия шаблона `templateId`.

#### 4.4.2. Подпись на бумаге (живая, с печатью)

1. Инициатор (сторона, отправившая запрос) формирует PDF и печатает **2 экземпляра** (или каждая сторона печатает свой).
2. Подпись, печать организации, дата — **вне системы**.
3. В карточке партнёра:
   - **«Мы подписали на бумаге»** — дата, ФИО подписанта, опционально **фото/скан** (как СТС у водителя).
   - Партнёр видит уведомление: **«Подтвердить получение подписанного договора»** — зеркальная отметка.
4. Когда `ourSignedAt` и `partnerSignedAt` заполнены и `signMethod === 'paper'` → `contract.status = 'signed'`.

> Галочка без PDF **не используется** — сначала всегда формируется документ, потом отметка о подписи.

#### 4.4.3. Подпись через оператора ЭДО (этап 6b, после MVP)

- Переиспользовать оболочку **`epd-sign.js`** (`openEpdOperatorShell`, webhook `/epd/webhook`) — тот же оператор, что для ЭТрН и КЭП логиста ([EPD_SIGN_ONBOARDING_PLAN.md](EPD_SIGN_ONBOARDING_PLAN.md)).
- Новый тип документа API: `POST /epd/partner-contract-sign-url` `{ partnerLinkId, side: 'our' | 'partner' }`.
- Оператор из `state.settings.epdOperator` (Контур / СБИС / Диадoc).
- Webhook обновляет `ourEdoMessageId` / `partnerEdoMessageId`, при `Signed` с обеих сторон → `contract.status = 'signed'`, `signMethod = 'edo'`.
- Fallback: если iframe запрещён — «Открыть в браузере» + «Обновить статус» (уже есть для ЭПД).

**До подключения API ЭДО:** кнопка «Через ЭДО» disabled с подсказкой «Подключите оператора в настройках платформы»; работает только бумажный канал.

#### 4.4.4. Единый статус в карточке партнёра

```
Договор: Не сформирован | PDF готов | Ожидает нашей подписи | Ожидает партнёра | Подписан (бумага) | Подписан (ЭДО)
[Сформировать PDF] [Печать] [Мы подписали] [Отправить в ЭДО — скоро]
```

- Тот же механизм расширяется на **рамочный договор заказчика** (`frameworkContract` в компании) — одна UX-модель для заказчика и партнёра-перевозчика.

### Этап 2 — Блок «Сотрудники»

**Задачи:**

1. Список `admins` с `spaceId === currentSpaceId()`.

### Этап 3 — Блок «Свой автопарк»

**Задачи:**

1. Объединить вкладки Компания / Водители / Авто / Тариф в одном блоке с подразделами.
2. «Профиль компании» — только `roles: ['own']` текущего space (уже есть «Профиль компании»).
3. Счётчики и быстрые действия: + водитель, + ТС, «Ссылка водителю».
4. Тариф — только для own-компаний **этого** кабинета (`catalogOwnCompaniesInView` — уже сделано).
5. Убрать дубли «Входы и ссылки» для водителя: кнопка в карточке водителя и в блоке парка.

**Критерий:** новый кабинет проходит чеклист пилота, не заходя в старые названия вкладок.

**Файлы:** `admin.js`, `index.html`.

### Этап 4 — Блок «Партнёры» — ручные контрагенты

**Задачи:**

1. Два списка: **Заказчики** и **Перевозчики** (фильтр `companyHasRole` + `!own` + `companyInMySpace`).
2. Кнопка «+ Заказчик» / «+ Перевозчик» → `openEditor` с предзаданной ролью (без «Наша фирма»).
3. Карточка заказчика: портал, PIN, рамочный договор (`frameworkContract` — уже есть).
4. Карточка перевозчика-ручного: ТС и водители вводятся вручную (как сейчас role carrier).
5. Бейдж источника: «локальный» vs «АРМАДА» (появится на этапе 5).

**Критерий:** логист Армады видит заказчиков и перевозчиков отдельно; портал заказчика включается из карточки.

---

### Этап 5 — Партнёр из сети АРМАДА (поиск и запрос)

**Задачи:**

1. Кнопка «Найти в АРМАДА» → поиск по ИНН / названию среди **других spaces** (API или индекс на `state.spaces` + `companies` с `roles: ['own']`).
2. Карточка найденного кабинета: название, ИНН, город, число ТС (агрегат без персональных данных).
3. Действие **«Запросить сотрудничество»** → создаёт `partnerLink` со статусом `requested`, уведомление в кабинет партнёра (inbox / push).
4. Партнёр видит запрос: «Армада хочет видеть ваш парк для совместных рейсов» — **Принять / Отклонить**.
5. До принятия — у заказчика только реквизиты и контакты (если партнёр разрешил), **без** водителей/ТС.

**API (если multi-tenant на сервере):**

- `POST /armada-api/partner-links` — создать запрос.
- `PATCH /armada-api/partner-links/:id` — accept/reject.
- Пока MVP на одном `state`: симуляция через `state.partnerLinks` + синхронизация при общем бэкенде.

**Файлы:** `store.js`, `admin.js`, `armada-api` (новые routes).

**Критерий:** MBN отправляет запрос Армаде; у Армады появляется входящий запрос; статус виден обоим.

### Этап 6 — Договор (PDF / бумага / ЭДО) и автоподтягивание парка

#### 6a. Рамочный договор (MVP — бумага)

**Задачи:**

1. После `partnerLink.status === 'active'` — блок **«Рамочный договор»** в карточке партнёра.
2. Шаблон `partner_framework` в конструкторе: две стороны, ИНН, предмет сотрудничества, перечень `shareScope`.
3. **«Сформировать PDF»** → preview + **«Печать»** (`openPrintHtml`, бланк с реквизитами и местами для подписи/печати).
4. Кнопки подписи нашей стороны: **«Мы подписали на бумаге»** (дата, ФИО, опционально скан).
5. Уведомление партнёру; у него — **«Партнёр подписал»** / загрузка своего скана.
6. `contract.status === 'signed'` только когда обе стороны отметили подпись (или загрузили сканы).
7. Тот же UX для **заказчика** — заменить простую галочку `frameworkContract` на PDF-поток (миграция без потери данных).

**Файлы:** `doc-templates.js`, `order-documents.js` или `partner-contracts.js`, `admin.js`, `store.js`.

**Критерий:** логист печатает договор с MBN, обе стороны отмечают подпись — статус «Подписан (бумага)».

#### 6b. ЭДО (когда API оператора готов)

**Задачи:**

1. Кнопка **«Отправить через ЭДО»** — `openEpdOperatorShell` с договором PDF.
2. API: `POST /epd/partner-contract-sign-url`, webhook → `contract.ourEdoMessageId` / `partnerEdoMessageId`.
3. Статус из оператора: «отправлен» → «ожидает партнёра» → «подписан обеими сторонами».
4. Если у партнёра другой оператор — обмен через роуминг ЭДО (вне MVP; в UI — предупреждение).

**Критерий:** при подключённом Контуре договор подписан без печати; sync парка доступен так же, как после бумаги.

#### 6c. Sync парка (после подписанного договора)

**Задачи:**

1. Кнопка **«Обновить данные парка»** активна только при `contract.status === 'signed'`.
2. Запрос к кабинету партнёра: водители и ТС по `shareScope`.
3. Запись в карточку перевозчика: `linkedDrivers`, `linkedVehicles` + метка «синх. …».
4. Повторный sync; diff; отзыв доступа → кэш «устарел».

**Ограничения:**

- PIN и пароли не передаются.
- Скан паспорта — только если партнёр включил в `shareScope.documents`.
- Партнёр может **отозвать** доступ (`revoked`).

**Критерий:** после подписанного договора (бумага или ЭДО) у логиста видны водители и ТС партнёра; обновление по кнопке.

---

### Этап 7 — Связь с биржей и заказами

**Задачи:**

1. На бирже «Забрать» доступно только для `partnerLink.status === 'active'` + договор signed (или исключение для разовых claim — решение продукт).
2. При claim подтягиваются актуальные водитель/ТС из `linkedFleet` (если sync свежий).
3. Заказчик-партнёр из сети: портал `/z` может быть на стороне партнёра; у нас — ссылка на его portal slug.
4. Интеграция с [EXCHANGE_PLAN.md](EXCHANGE_PLAN.md): партнёр ≠ аноним; cargoFingerprint не ослаблять.

**Критерий:** цепочка «запрос → договор → sync парка → claim на бирже → назначение водителя» проходится end-to-end на двух тестовых кабинетах.

| 4 | **2 — сотрудники** | Owner приглашает логистов (MBN, Нечаев) |
| 5 | **5–6a — сеть + PDF-договор** | Запрос партнёра + бумажная подпись |
| 6 | **6b — ЭДО** | После API оператора |
| 7 | **6c + 7 — sync + биржа** | Парк и claim |
| 8 | **8 — полировка** | Документация, онбординг |

Этапы B/D/E из [plan-seti.html](../plan-seti.html) **встраиваются**: B → блок «Партнёры → Заказчики»; D → «Найти в АРМАДА»; E → этапы 6a–6c (PDF, ЭДО, sync).

## 7. Риски и решения

| Риск | Решение |
|------|---------|
| Дубли водителей при sync | Ключ `(sourceSpaceId, sourceDriverId)`; не merge с own fleet |
| Утечка документов | `shareScope` явно; аудит `partnerLink` |
| Партнёр удалил водителя | `lastSyncAt` + бейдж «нет на стороне партнёра» |
| Два owner в space | Один `ownerAdminId` на space; смена только супер-админом |
| Логист путает «Профиль компании» и «Профиль логиста» | Разные блоки; подсказки уже есть |

## 8. Критерии «кабинет логиста готов» (Definition of Done)

- [ ] Один экран настроек с тремя блоками.
- [ ] Owner управляет логистами без супер-админа.
- [ ] Парк и тариф настраиваются без «Справочников» в меню.
- [ ] Заказчики и перевозчики разделены; ручное добавление работает.
- [ ] Поиск партнёра в АРМАДА + запрос + принятие.
- [ ] PDF договора: формирование, печать, двусторонняя отметка «подписан на бумаге» (+ скан).
- [ ] ЭДО: отправка и статус через оператора (когда API готов).
- [ ] После подписанного договора — sync водителей и ТС по кнопке логиста.
- [ ] Биржа использует только активных партнёров с договором (или явное исключение в настройках space).
