## Разделение: платформа vs кабинет клиента

| Что | Супер-админ (Армада) | Логист (любой кабинет с тарифом ЭТрН) |
|-----|----------------------|----------------------------------------|
| Ключ разработчика Контура | ✅ только на VPS (`armada-api/.env`) | ❌ |
| Письма **оператору Контура** (API, ключи, sandbox) | ✅ `operator-letters.js` | ❌ |
| Журнал API / webhook платформы | ✅ Активность → ЭПД | ❌ |
| **boxId** своей организации | ✅ вводит супер-админ | 👁 «подключено» / «ждём» |
| Подпись T1–T4 по заявкам | ✅ | ✅ |
| Шаблоны писем **оператору подписи** (выпуск КЭП/ПЭП) | ✅ эталон | ✅ на **бланке клиента** |
| Фирменный бланк, логотип | свой кабинет | ✅ только **их** реквизиты; внизу мелко «Сформировано в сервисе Армада» |

**Платформенные настройки Контура для клиента** = модуль ЭТрН включён в тарифе + привязка **их** юрлица (boxId) + подписи + обмен титулами через сервер Армады (один ключ разработчика, маршрутизация по `spaceId`).

## Этапы реализации

### Этап 1 — Заказы + бланки + шаблоны писем *(готово в коде, 2026-09-02)*

1. Бейджи ЭТрН и фильтр «нужна моя подпись» в списке заказов.
2. Улучшить блок ЭТрН в карточке заказа.
3. **Шаблоны писем оператору подписи** — редактирование, печать/PDF на бланке **клиента** (логотип + реквизиты «нашей фирмы»).
4. Письма «Армада → Контур» — **только супер-админ** (убрать из клиентских кабинетов).
5. Бланк: шапка = клиент; footer = «Сформировано в сервисе Армада».

**Критерий:** логист видит в списке, где нужна его подпись T2; может распечатать письмо на подключение подписи на своём бланке.

---

### Этап 2 — Multi-tenant на сервере

- Один `KONTUR_CLIENT_ID/SECRET` на платформу; у каждого `space` — свой `boxId` / ИНН в `state.epdBySpace[spaceId]`.
- API: `GET/PUT /epd/space/:spaceId`; `POST /orders/:id/etrn` маршрутизирует по `order.spaceId`.
- Webhook обновляет титулы с привязкой к space.
- ЭТрН для любого кабинета с `billing.spaces[id].etrnEnabled`.

**Критерий:** smoke — ЭТрН заказа пилота уходит в **его** ящик (sandbox).

---

### Этап 3 — Подписи T1–T4 «из коробки»

- `POST /epd/sign-up-url`, `/epd/titul-sign-url`, `/epd/sign-status` на armada-api.
- Заказчик T1 (`/z`), логист T2 (профиль), водитель T3/T4 (приложение).
- Sandbox → бой. Пилоты: Нечаев, МБН; далее — новые клиенты с тарифом Business+.

**Критерий:** полный цикл T1→T4 на тестовой заявке (sandbox), затем один боевой рейс на проде.

---

### Этап 3b — Входящая ЭТрН → автозаявка *(не реализовано)*

**Сейчас:** только исходящий поток **заявка → ЭТрН** (`POST /orders/:id/etrn`).  
`POST /epd/webhook` (план) обновляет **существующий** заказ (`order.etrn.tituls`), **не создаёт** новый.

**Цель:** если ЭТрН оформлена **сторонним сервисом** или **у оператора ЭПД** (Контур и др.) и **перевозчик указан в документе / документ пришёл в ящик клиента**, в АРМАДА **автоматически** появляется **заявка** с привязанным блоком ЭТрН (без ручного заведения рейса).

#### Когда документ «виден» платформе

| Ситуация | Попадёт в АРМАДА? |
|----------|-------------------|
| ЭТрН в **вашем boxId** у оператора (вы — перевозчик в цепочке) | ✅ после интеграции |
| ГО оформил «у себя», **вас не указали**, ваш boxId не в обмене | ❌ |
| Сторонний TMS/ATI шлёт webhook/API | ✅ если подключён канал |
| Только файл/XML без API | ⚠️ полуавтомат (импорт), не «в фоне» |

#### Каналы (приоритет)

1. **Оператор ЭПД (Контур — основной)** — webhook и/или опрос API: событие «новый документ ЭТрН / подписан T1» → разбор титула → создание заказа.
2. **Партнёрский логистический сервис** — webhook (ATI, TMS заказчика): те же шаги маппинга; можно позже на базе partner-links (`LOGIST_CABINET_PLAN`).
3. **MVP** — уведомление + черновик + кнопка «создать заявку из накладной» (без полного автопарсинга).

#### Серверный поток (armada-api)

| Шаг | Действие |
|-----|----------|
| A | Приём события: `POST /epd/webhook/inbound` или расширение `/epd/webhook` типом `document.created` / `titul.signed` |
| B | Получение/разбор XML/JSON титула (T1 минимум): ГО, получатель, маршрут, груз, ИНН перевозчика, id документа у оператора |
| C | **Tenant:** ИНН перевозчика в накладной → `spaceId` / компания (`state.epdBySpace`, заказ `spaceId`) |
| D | **Дедуп:** ключ `order.etrn.externalDocId` (или `konturWaybillId`) — повторное событие не создаёт вторую заявку |
| E | **`createOrderFromEtrn(payload)`** — новый заказ (статус «входящая из ЭТрН») + `order.etrn` с id оператора и статусами титулов |
| F | Журнал в **Активность → ЭПД**; опционально push/бейдж «новая входящая ЭТрН» |

#### UI

- Фильтр / колонка: **«Входящие ЭТрН»** (создано из оператора vs создано вручную).
- Карточка заказа: источник `etrnSource: 'inbound' | 'armada'`, ссылка на документ в операторе (если есть).
- Канбан «Входящие» — те же заявки, что требуют назначения водителя/T2 после T1.

#### Правила (обязательно)

1. Внешний **id документа** — уникальный ключ; без него — дубли заявок.
2. Автосоздание заказа **≠** автоподпись T2 — перевозчик подписывает по своему процессу (`etrn.js` / `openEpdTitulSign`).
3. Первый контур интеграции — **один оператор** (Контур); второй оператор / ATI — тот же контракт payload.
4. Только кабинеты с **`etrnEnabled`** в тарифе.

#### Зависимости

- Этап **2** (multi-tenant, webhook в **свой** boxId по `spaceId`).
- Этап **3** (T1–T4 in-app) — для подписей после появления заявки.
- Ключи Контура на VPS, boxId пилотов (см. блокеры ниже).

**Критерий приёмки (sandbox):** в ящик пилота приходит тестовая ЭТрН «снаружи» → в кабинете появляется **новая заявка** с корректными полями маршрута/ГО и бейджем ЭТрН; повтор webhook **не** дублирует заказ.

**Файлы (целевые):** `armada-api` routes `epd/webhook`, новый handler inbound; `store.js` / `order` модель; `etrn.js` — источник заявки; `admin.js` — фильтр входящих.
