# План: биллинг SaaS — счета, активация, закрывающие, подписка

Статус: **M0 в коде** · онлайн-оплата и закрывающие SaaS — **не внедрены**.

Связано: `billing.js`, `admin.js` → «Тарифы», `legal.html` (оферта SaaS).

---

## Ответы на вопросы (как сейчас vs как будет)

### 1. Как будут выставляться счета за сервис?

**Сейчас (M0 — ручной режим):**

- Супер-админ **вне системы** выставляет счёт из 1С / банка / шаблона на реквизиты ООО «АРМАДА».
- В приложении: **Админ → Тарифы** (только супер-админ) → поля «₽ оплата» + «счёт/акт» → **«Записать оплату»** (`recordManualPayment`).
- Автоматического PDF «Счёт за подписку АРМАДА» **нет**.

**План (M1 → M2):**

| Этап | Как |
|------|-----|
| **M1** | Кнопка «Сформировать счёт» в кабинете → PDF/HTML на бланке ООО «АРМАДА»: тариф, период, сумма, QR СБП (как у счетов заказчику в `customer-invoice.js`, но для SaaS). |
| **M2** | Онлайн: ЮKassa / Тинькофь / счёт по API → webhook `processPaymentWebhook` → продление `subscriptionEndsAt`. |

Плательщик — **space перевозчика** (юрлицо из «нашей фирмы» / реквизиты space), не заказчик с портала `/z/`.

---

### 2. Где это будет учитываться?

**Сейчас — в `state.billing.spaces[spaceId]`** (синхронизируется через PocketBase / armada-api в общем state):

| Поле | Назначение |
|------|------------|
| `planId` | start / business / pro / … |
| `status` | trial · active · grace · readonly · suspended |
| `trialEndsAt` | конец пилота (30 дн. по умолчанию) |
| `subscriptionEndsAt` | оплачено до |
| `graceEndsAt` | 7 дн. после истечения оплаты |
| `manualPayments[]` | ручные оплаты (сумма, дата, note) |
| `ledger[]` | журнал: оплаты, комиссия биржи |
| `balance` | баланс (минус = долг по комиссии биржи) |

**Не путать:**

- `state.invoices[]` + `customer-invoice.js` — счета **перевозчика своему заказчику за перевозку**, не за SaaS.
- `order-documents.js` — договоры/акты **по заявкам**, не подписка платформы.

**План M1:** отдельный массив `state.billing.invoices[]` или `billing.spaces[id].saasInvoices[]` — счета/акты **за подписку** с номером, периодом, статусом оплаты.

### 3. Как будет происходить активация пользователя?

**Сейчас:**

```
Создан space + админ (PIN)
    → migrateBilling() → trial 30 дн., status=trial
    → billingCanWrite() = ok до trialEndsAt
После пилота без оплаты
    → resolveBillingStatus() = readonly
    → billingGuard блокирует create_order, add_driver, …
Активация после оплаты
    → recordManualPayment() → subscriptionEndsAt += N×30 дн., status=active
```

Супер-админ может: сменить тариф, **+30 дн. пилот**, записать оплату.

**Нет:** самoregistration, оплаты картой, письма «добро пожаловать» с invoice.

**План:**

| Шаг | Действие |
|-----|----------|
| 1 | Заявка на пилот (`pilot.html`) → супер-админ создаёт space + админа |
| 2 | Trial автоматически (как сейчас) |
| 3 | За 7 дн. до конца — баннер + email «оплатите / продлите пилот» |
| 4 | Оплата (ручная M1 / онлайн M2) → `active` |
| 5 | Просрочка → grace 7 дн. → readonly |

---

### 4. Как и куда отправляются закрывающие документы?

**Сейчас: никак автоматически.**

- Поле «счёт/акт» при записи оплаты — только **текст в журнале** (`ledger.note`).
- PDF акта/счёт-фактуры за **SaaS** не генерируется.
- Закрывающие по **перевозкам** — через «Документы» по заявке (акт, счёт заказчику) — это другое.

**План M1:**

1. После оплаты (или по кнопке супер-админа) — **Акт оказания услуг SaaS** + при необходимости счёт-фактура (если АРМАДА на НДС).
2. Шаблон на фирменном бланке ООО «АРМАДА» (`operator-letters.js` / doc-templates).
3. Отправка: **email** на `billingEmail` space (новое поле) + скачать в **«Подписка»** в кабинете админа.
4. Хранение: `saasInvoices[]` / `saasActs[]` с `sentAt`, `documentId`.

---

### 5. Где пользователь видит окончание подписки?

**Сейчас:**

| Кто | Где |
|-----|-----|
| Обычный админ | Жёлтый баннер `#admin-billing-banner` под шапкой: «Тариф: Бизнес · Пилот · пилот до ДД.ММ» или «оплачено до …» |
| Супер-админ | Экран **«Тарифы»** — все space, даты, журнал |

**Нет:** отдельного экрана «Подписка», email-напоминаний, видимости для водителя/заказчика.

**План M1:**

- Пункт меню **«Подписка»** (или блок в «Профиль») для каждого админа space:
  - тариф, статус, **пилот до / оплачено до**
  - кнопка «Скачать счёт» / «Запросить акт»
  - история платежей
- Push/email за 14 / 7 / 1 день до `trialEndsAt` / `subscriptionEndsAt`.

## Этапы внедрения

### M0 — сейчас ✅

- [x] Тарифы, trial, grace, readonly
- [x] `billingGuard` / API guard
- [x] Ручная запись оплаты (супер-админ)
- [x] Баннер в админке
- [x] Комиссия биржи в ledger

### M1 — счета и видимость (4–6 задач, без онлайн-оплаты)

1. **UI «Подписка»** для админа space (не только супер-админ): даты, тариф, CTA «Связаться / оплатить».
2. **Генерация счёта SaaS** — PDF на бланке АРМАДА, номер, период, сумма по `BILLING_PLANS`.
3. **`saasInvoices[]`** в billing state + persist/sync.
4. **Шаблон акта SaaS** + привязка к записи оплаты.
5. **Email** (armada-api): отправка счёта/акта на `billingEmail`.
6. **Smoke:** trial → readonly → оплата → active; баннер и экран совпадают.

**Не ломать:** guards, `/a` вход, sync, счета заказчику за перевозки.

### M2 — онлайн-оплата

1. ЮKassa (или Тинькофь) — payment link / СБП QR.
2. Webhook на armada-api → `processPaymentWebhook` (уже stub в `billing.js`).
3. Автопродление + grace (как сейчас логика, триггер от webhook).
4. idempotency, лог платежей.

### M3 — автоматизация

1. Напоминания email/Telegram за N дней до конца.
2. Автосчёт за месяц (cron на VPS).
3. Сверка с 1С (export CSV/API) — опционально.
